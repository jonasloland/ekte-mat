# Plan 0006 – Neo4j som lagring (oblig 5)

**Status:** Gjennomført (godkjent av Jonas 2026-11-04)

## Kontekst
Gruppa vil levere oblig 4 og 5 samtidig. Oppgaveteksten sier at hvis lagringslaget allerede er
implementert med Neo4j og det står på forsiden, teller innleveringen også som oblig 5. Appen er
bygd for dette: controllere og maler bruker bare de abstrakte grensesnittene i
`app/models/repositories/base.py`, og `create_repositories()` i `repositories/__init__.py` velger
implementasjon ut fra `STORAGE_BACKEND`. Neo4j blir derfor én ny implementasjon, uten endringer i
controllere, maler eller forretningslogikk. Neo4j kjører i Docker (valgt av Jonas).

Arbeidet gjøres på branchen `neo4j-lagring`. Denne planen committes først som
`docs/plans/0006-neo4j.md`, før koden (teamregel 4).

## Grafmodell
```
(:User {id, email, name, password_hash, role})
(:Dish {id, name, description, price_nok, min_order, published, image_path, image_prompt, origin})
(:Allergen {key}) (:Diet {key}) (:EventCategory {key})
(:Order {id, event_date: date, guest_count, delivery_address, status, payment_status, created_at: datetime})
(:OrderLine {pos, dish_id, dish_name, unit_price_nok, quantity, allergens: [str]})
(:GuestGroup {pos, name, count, notes})
(:Question {id, body, created_at, answer, answered_at})
(:Counter {name, next})            // gir heltalls-id-er, så URL-ene /retter/3 osv. virker som før

(Dish)-[:CONTAINS]->(Allergen)   (Dish)-[:SUITS]->(Diet)   (Dish)-[:SERVED_AT]->(EventCategory)
(User)-[:PLACED]->(Order)-[:HAS_LINE]->(OrderLine)-[:OF_DISH]->(Dish)
(Order)-[:HAS_GROUP]->(GuestGroup)
(User)-[:ASKED]->(Question)-[:ABOUT]->(Order)      (User)-[:ANSWERED]->(Question)
```
Valg:
- **Allergener, dietter og anledninger som noder**, ikke lister. Det er det grafen er god til, og
  `list_published(event_category)` blir en traversering.
- **OrderLine som egen node** med kopi av navn, pris og allergener, som i SQLite. Slettes en rett,
  forsvinner bare `OF_DISH`-relasjonen; gamle ordrer er uendret.
- **Heltalls-id-er via `:Counter`** (atomisk `MERGE … SET c.next = coalesce(c.next, 0) + 1`), slik at
  domeneklassene, rutene og testene ikke må endres.
- Unikhetskrav (constraints) på `id` per label og på `User.email`, opprettet i `init_schema()`.

## Endringer
1. **`app/models/repositories/neo4j.py`** (ny, eneste sted med Cypher)
   - `Neo4jDatabase(uri, user, password, database)`: driver, `session()`-hjelper, `init_schema()`
     (constraints), `reset()` (`MATCH (n) DETACH DELETE n`), `next_id(name)`, `close()`.
   - `Neo4jUserRepository`, `Neo4jDishRepository`, `Neo4jOrderRepository`,
     `Neo4jQuestionRepository` som implementerer alle metodene i `base.py`, med samme sortering som
     SQLite-versjonen (retter etter navn, ordrer etter eventdato, spørsmål etter tidspunkt).
   - `Dish.update` erstatter relasjonene til allergener/dietter/anledninger.
   - `Order.add` skriver ordre, linjer og grupper i én transaksjon; `customer_name` hentes via `PLACED`.
   - `guests_on_date` summerer `guest_count` for aktive ordrer (ikke avvist/kansellert).
   - Datoer lagres som Neo4j `date`/`datetime` og konverteres med `.to_native()`.
2. **`app/models/repositories/__init__.py`**: gren for `STORAGE_BACKEND == "neo4j"` (lat import, så
   SQLite virker uten driveren) i både `create_repositories()` og `reset_storage()`.
3. **`app/config.py`**: `NEO4J_URI` (standard `bolt://localhost:7687`), `NEO4J_USER`,
   `NEO4J_PASSWORD`, `NEO4J_DATABASE`, lest fra miljøet.
4. **`.env.example`**: Neo4j-variablene og `STORAGE_BACKEND=neo4j` som kommentert alternativ.
5. **`requirements.txt`**: `neo4j` (driver, fast versjon).
6. **Tester**
   - `tests/test_repositories.py` (ny): kontrakttester for alle repository-metodene, parametrisert
     over backendene. SQLite kjører alltid; Neo4j kjører med `TEST_STORAGE_BACKEND=neo4j`, ellers `skip`.
     (Endret under implementering: `NEO4J_URI` kommer fra `.env`, så det ville tømt dev-databasen ved et uhell.)
   - `tests/conftest.py`: `TEST_STORAGE_BACKEND=neo4j` kjører **hele** testsuiten mot Neo4j
     (databasen tømmes før hver test). Standard er fortsatt SQLite, så `pytest` virker uten Docker.
7. **Dokumentasjon**
   - `README.md`: seksjon «Kjøre med Neo4j» (Docker-kommando, `.env`, seed, kjøre, teste), og
     oppdatert arkitektur-avsnitt.
   - `CLAUDE.md`: `neo4j.py` er eneste sted med Cypher; slik bytter man backend.
   - `docs/plans/0006-neo4j.md`: denne planen.
8. **Rapport** (`~/INFO212/rapport`, utenfor repoet): forside «Neo4j inkludert: Ja», grafmodell
   som diagram under Programvaredesign, og MVC-skissen oppdatert (Neo4j ikke lenger stiplet).

Ingen endringer i `controllers/`, `templates/`, `entities.py`, `services.py` eller `cart.py`.

## Neo4j i Docker
```bash
docker run -d --name ektemat-neo4j -p 7474:7474 -p 7687:7687 \
  -e NEO4J_AUTH=neo4j/ektemat-passord neo4j:5.26
```
Docker Desktop må være startet først. Nettleseren til Neo4j: http://localhost:7474.

## Verifisering
1. `python -m pytest -q` uten Neo4j: alle eksisterende 46 tester + nye SQLite-kontrakttester består,
   Neo4j-testene hoppes over.
2. Start Neo4j i Docker. `TEST_STORAGE_BACKEND=neo4j python -m pytest -q`: hele suiten og
   kontrakttestene består mot Neo4j.
3. `STORAGE_BACKEND=neo4j python seed.py && PORT=5055 python run.py`: gå gjennom meny, handlekurv,
   bestilling, mine bestillinger, spørsmål, adminpanelet (retter, bilde, bestillinger, status,
   CSV, kjøkken) og se at alt virker som med SQLite.
4. Se grafen i Neo4j Browser (`MATCH (n) RETURN n LIMIT 100`), og ta et skjermbilde til rapporten.
5. Commit på `neo4j-lagring`; Jonas lager PR, en annen i gruppa merger. Deretter lages taggen
   `oblig4` på den nye `main`.
